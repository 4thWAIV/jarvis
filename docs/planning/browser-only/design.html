Your JARVIS, available from a browser.

Keep the interface. Give each owner a hosted personal instance. Run conversations, files and agent work on the server, with no desktop installation required.

The tradeoff for review. The browser can reach your hosted workspace from another computer or phone. It cannot automatically reach that computer’s files, terminals or applications. A separately paired local JARVIS could provide those capabilities later.

The gateway is a logical responsibility, not necessarily a new service. It can begin within the hosted web service, reusing Team Server’s session verification. Requests are routed using authenticated ownership, never a browser-supplied filesystem path or an unchecked instance identifier.

Retain one personal runtime per owner initially. Multiple browser sessions attach to that runtime; they do not each create a new brain or copy of the database. Do not combine every owner’s existing Python globals and filesystem state into one shared JARVIS process.

Deployment and isolation

Keep Team Server on its existing deployment path. Run hosted personal instances and execution workers separately from it. A Railway-hosted control service is a candidate, but persistent-volume lifecycle, private routing, provisioning and resource limits must be demonstrated before choosing Railway for every runner. This proposal does not claim that those services or volumes already exist.

Each runtime has one writable persistent data volume and one active database writer process. A deployment must stop or fence the previous writer before attaching a replacement. Do not place the SQLite file on a shared multi-writer network filesystem.

Repository code runs in a separate restricted execution environment, without the host’s container-management socket, Team Server administrative credentials or access to other owners’ volumes. Use workspace mounts, scoped tool access, process-tree cancellation, CPU/memory/disk quotas and restricted credentials. A container alone is not the complete isolation design; runner escape and cross-owner access tests are release gates.

Authentication and approval boundaries

Reuse GitHub identity and Team Server’s browser-session model. Use secure HttpOnly session cookies, CSRF protection on mutations, authorized WebSocket handshakes and revocation checks. Authenticate reads as well as writes. Keep origin and host checks as additional protections; localhost’s origin-only admission is not public authentication.

Resolve the owner and team membership on the server. Issue scoped internal service credentials to the personal instance. Never place provider secrets, database credentials or reusable node tokens in browser local storage, URLs or logs.

Preserve JARVIS’s existing human-review behavior for outgoing messages and actions. An authenticated human click authorizes the displayed revision; agent-originated requests cannot forge it. This reuses application approval behavior rather than introducing a separate approval product. Retry handling must not approve or send a message twice.

Conversation and compute lifecycle
  1. The runtime maps each JARVIS conversation to its provider, provider-session reference and working location. Store that association durably rather than in a browser tab.
  2. A submitted turn gets an idempotency key. Reconnecting or retrying a request returns the existing turn or job rather than launching another.
  3. Store durable milestones and outputs with a monotonically ordered event cursor. Stream live output; batch persistence rather than writing every token as a separate database transaction.
  4. On reconnect, return current state and events after the last acknowledged cursor. If the cursor has expired, send a fresh snapshot and available history.
  5. Only one foreground microphone session controls a conversation at a time. Another tab can observe or explicitly take over. Serialize competing turns and approvals.
  6. A closed tab detaches the viewer. Explicit cancellation stops the job’s process tree and records its terminal state.
  7. After a server crash, reconcile persisted jobs with surviving workers. Use supported provider resume where available. If execution status is uncertain, mark it interrupted and reconcile side effects before offering retry; never silently repeat a send or deployment.

Context compaction, session cycling and forks stay provider-aware. A browser reconnect resumes viewing; it does not imply starting a fresh provider context. A new cloud session cannot automatically inherit local CLI transcripts without a separate, explicit import design.

Files, retention and recovery

Reuse attachment validation, snapshots and message revision handling. Enforce upload limits before and during transfer; stream into temporary private files, validate completion and promote atomically. Keep shared message attachments under their existing protocol and ownership rules.

Back up SQLite with its supported backup mechanism, together with a versioned manifest of the associated workspace/history snapshot. Test restore into an isolated runtime. Provider credentials need a separate encrypted recovery policy or reauthentication.

Before a production release, choose retention, deletion, recovery-point and recovery-time targets. These affect volume and backup cost. They are unresolved product decisions, not settings already configured by this document.

The initial design keeps the current model and voice output. Network transit is added to recognition; no claim of equal latency is made until measured. Preserve bounded audio queues and explicit overload reporting. Do not discard the beginning of a command to catch up, and do not replay stale microphone audio automatically after reconnect.

Measure capture-to-partial, end-of-speech-to-final, first-response audio, recognition accuracy, interruption latency, queue depth and memory on the i9 Mac and M1 Mac. Test ordinary Wi-Fi, constrained bandwidth, packet loss, simultaneous agent load and a suspended/resumed tab. Keep the existing echo-cancellation path and test readback with an open microphone.

Browser-local speech recognition is a later optimization candidate. sherpa-onnx offers WebAssembly Zipformer examples, but the exact model, download size, cold start, browser scheduling and mobile memory still require qualification. It is excluded from the initial estimate. Microphone audio would leave the device in the proposed initial hosted mode; make that visible in the product’s voice settings.

Provider authentication is a design gate

Keep the existing provider interface and implement hosted authentication through supported provider paths. Do not copy the developer machine’s subscription credentials into a shared service.

OpenAI’s App Server documentation states: App-server authentication has never been permitted for commercial or hosted services. Its recommended hosted direction is Sign in with ChatGPT. Establish access to that integration or select supported API authentication before including hosted Codex subscription use in a build commitment. OpenAI source.

Anthropic documents hosting the unmodified Claude Code binary with end users completing supported authentication and paying for their own usage. This differs from offering a custom Claude subscription login or intermediating users’ OAuth credentials. Review the full conditions when choosing the hosted provider implementation. Anthropic source.

GitHub login identifies the JARVIS owner; it does not authenticate that owner to a model provider. Provider sign-in remains a separate, explicit onboarding step. API billing must not be represented as automatically covered by a subscription.

Behavior when something goes wrong

Network disappearsShow disconnected state, stop accepting live microphone input, preserve unsent text visibly, reconnect with event replay. Hosted jobs continue.
Provider session expires or quota is reachedShow the specific provider state and recovery action. Do not silently switch to chargeable credentials or another account.
Runtime restartsRestore records, reconcile worker state and show interrupted work honestly. Do not manufacture successful completion.
Disk, memory or execution budget is exhaustedReject new work with a clear reason; preserve results and provide cancellation or cleanup controls. Enforce quotas below the UI.
Owner signs out or access is revokedRevoke browser access and event streams. Ordinary sign-out leaves jobs running; membership revocation applies the configured suspension policy.
Local node is unavailableShow its capabilities as unavailable. Do not substitute a hosted file or execute the same command in another location.

The browser’s activity reports describe interaction with JARVIS, not activity in unrelated applications. Hosted node health and last human interaction remain separate measures. Reuse the existing network reporting contract rather than equating an open tab with an active human.

After the feasibility proof, identity/routing, runtime/data, and interface/voice can proceed in parallel against agreed request and event contracts. Isolation, restart recovery and provider authentication carry the most uncertainty. A gateway or UI prototype alone does not establish completion.

Proposed milestones, if approved later
  1. Prove the journey. Log in from a second machine, send a typed turn, speak, attach a file, start a repository task, close the tab and recover its result. Demonstrate a supported provider login and record voice timing.
  2. Separate owners. Provision two owners and prove that HTTP, WebSockets, files, provider sessions and execution remain separate. Use self-messaging for routine checks and a second test identity for isolation.
  3. Recover work. Exercise duplicate requests, cancellation, runtime crashes, expired credentials, lost connectivity, disk limits and restoration from backup.
  4. Qualify the release. Test Chrome/Edge, Safari and Firefox on desktop; physically test iOS Safari and Android Chrome for the supported mobile scope. Publish a capability matrix based on results rather than browser names alone.
  5. Stage and release. Run focused local checks, integrate the completed change set, then perform a staged end-to-end acceptance pass. Batch deployment checkpoints rather than deploying each agent’s intermediate edit. Keep the current desktop path operational.

Ongoing cost would include personal runtime memory, active job CPU, recognition CPU, workspace storage, backups, network transfer and provider usage. Model cost per active owner and per idle owner before selecting an always-running policy. No monthly price is quoted without workload measurements and a hosting choice.
