# Architecture packages as presentations

Status: proposal, not built. Nothing in this document is implemented, and none of it changes the language kit.

## Summary

An architecture package today shows one drawing of one checked document: the language kit's catalogue of declarations. When a package carries several documents (a view set), each is a further catalogue in the same language, so the package still offers one kind of view. The story told over it is a list of narration beats that point at parts of that drawing, and the questions it asks open as cards over it. It is not a presentation in the sense other packages are.

This proposal expresses the architecture as the slides of a presentation (presentation/1). Each slide is one view of the system: its context, its containers, its components, a runtime scenario, its deployment, its exact surface and the decision being asked. Every view is generated by a program from the one checked architecture source, so the views cannot disagree with each other or with the source. The vote and the architecture approval keep their meaning: Tim approves an exact checked revision of the source, and the drawings are derived from it.

## What an architecture package is today

### The language and the kit

The architecture language is `arch`, defined in `arch.yaml` and written in MetaLang (`metalang.yaml`). A third file, `propose.yaml`, is the proposal language. These three are the kit's language files (`LANGUAGE_FILES` in `jarvis/language_kit.py`). The kit also carries `kit.js`, which checks a document and renders it, and `page.js`, the bundle of the rendered page. JARVIS pins one kit release, stages it, smoke-tests it and activates it by digest under the data folder (`jarvis/language_kit.py`). A newer upstream release is fetched every six hours, and one whose language files differ from the active kit's waits for Tim's review (`jarvis/language_kit_updates.py`).

What `arch` can say today, from `arch.yaml`:

- An element is one named piece of an architecture with a form: interface, class, record, enum, function or process.
- An element has members, each of one kind: method, constructor, property, field or value.
- An element has a reach (public, internal, private) and an exactness (loose, exact).
- An element sits in a package, an assembly and a namespace (the three places).
- An element relates to other elements in three ways: it implements one, answers with one, or holds one.
- An element belongs to groups, each a concept or a job.

All of it is about how code is organised. The language has no word for a person or an external system, for one element calling another with a stated purpose, for a sequence of interactions, for a machine or environment something runs on, or for the reason a choice was made.

### Documents and revisions

A document is checked as a proposed revision on a Work item (`jarvis/language_documents.py`, `Documents.validate`). The revision identity is computed from the document id, the source hash, the kit digest, the metadata and the parent revision (`revision_for`). Documents live in the records at `/language/<id>.langdoc`. Only the language `arch` may be published as an architecture view (`VIEW_LANGUAGES`).

### The package

An agent sends an architecture with `make_package --document <id> --revision <rev> ...` (`jarvis/make_package.py`, `docs/making-a-package.md`, "Architecture documents"). A fresh author writes `UNDERSTANDING.md`, the plain explanation, and optionally `story.json`. The factory projects the checked revision into a page package (`jarvis/language_projection.py`, `project`): the exact source, the checker's evidence, the kit's rendered page as the package's `index.html`, the canonical identity in `canonical.json`, the explanation and the story.

Giving `--document` and `--revision` more than once makes a view set of at most six checked documents (`SET_MAX`). The first is the package's own revision and the others are bound beside it in `canonical.json`. Each is checked again by the receiving JARVIS (`gate`), and each must be in a language of `VIEW_LANGUAGES`, which is `arch` only. A set must have a story that walks one concrete scenario through every view in turn (`package_story.walk_problem`).

### The story

The story is composed by the factory from the author's story and the vote (`package_story.compose`). The receiving JARVIS admits the package only when its story is byte for byte the composition (`language_projection.gate`). The author may write slides, beats (narration), targets (selectors such as `[data-declaration="DocumentStore"]`), questions and `asks_when`, but not a layout, a picture or a diagram, because a story points at what the kit's page already draws.

### The page

The package opens in the centre as a page package (`frontend/src/PackageView.tsx`): the kit's page in a sandboxed frame, with the icon border above it (`PackageBorder.tsx`) and the focus layer over it (`PackageFocus.tsx`). A view set shows one view at a time in the frame, and the border's Chapters name each slide's view and move between them. The frame's helper (`jarvis/package_story.js`) rings the targets of a beat and lights an element he clicks in every view that shows it.

What can be done while it shows:

- Scroll the drawing and click an element to light it.
- Tell the story, pause it, stop it and return to a kept place.
- Open the explanation, a card centred over the whole view that dims it to 25 percent.
- Open a question, a card beside the part it is about, with the rest dimmed to 55 percent.
- Move between views of a set with Chapters.
- Done, which signs the package off.

The dim and the light layer take no clicks, but each card takes keyboard focus while it is open and Escape is the way out.

### The vote

When the handoff asks for his approval, the story's last slide asks `approve-architecture` (Approve or Request changes) in place of the standard `approve-package` vote, so the package carries no vote at Done (`make_package._with_vote`). His answer is recorded with the exact checked revision of every view (`package_inbox.subject_of`) and is stale once a newer revision is checked or a kit with different language files comes into force (`language_projection.current_subject`).

## Why it is one view

1. The only drawing is the kit's catalogue. `page.js` draws each declaration as a card with its members, reach, exactness, places and relations as lists. No relation is drawn as a line between two elements, so a reader cannot see structure at a glance, only read it.
2. A view set is several documents in one language, not several kinds of view. The two views in the existing tests are both `arch` catalogues of different declarations. `VIEW_LANGUAGES` holds one entry.
3. The language cannot say what other views need. There is nothing to draw for a context (no external actor), a runtime scenario (no sequence), a deployment (no place a thing runs) or a rationale (no decision record).
4. The author cannot compose slides. A story points at selectors inside a drawing it did not make, and the gate compares the story with the factory's composition byte for byte. A slide cannot hold a figure, a chart, a picture or a diagram of its own, which every other package's slides can.
5. The explanation is a separate document. The purpose, the conclusion and the walk-through are in `UNDERSTANDING.md`, read in a card over the drawing, instead of being the opening slides.
6. The questions interrupt the drawing instead of belonging to a slide. A card is opened over the page and closed with Escape, where other packages ask a decision on its own slide.

## The proposal

### Architecture as slides of presentation/1

An architecture package becomes a deck. Its slides are drawn with the objects presentation/1 already has (`jarvis/presentation_schema.py`): the diagram kinds flow, cycle, hierarchy and timeline with node shapes, tones and connector styles, tables and charts from data, steps, key figures, callouts, pictures and text. JARVIS lays every diagram out by program (`jarvis/diagram_layout.py`) and checks every slot against its capacity (`jarvis/deck_capacity.py`), as for any deck. The deck is delivered with the proof the pipeline already makes (`presentation_proof.py`).

### One source, generated views

The author does not draw. The author supplies the checked architecture source (as today), the narration for each view, and which views to include. A program, the view generator, reads the checked document and writes the slides:

| View | What it shows | Drawn as | From |
|---|---|---|---|
| Context | The system, the people and systems around it | flow | new words (see below) |
| Containers | The packages and assemblies the system ships as, and what sits in each | hierarchy | `sits` |
| Components | The elements inside one container and how they relate | flow, one slide per container | `relates`, `form` |
| Runtime scenario | One scenario, step by step, between the parts | flow or timeline | new words |
| Deployment | What runs where | hierarchy | new words |
| Surface | Each element's exact members, reach and exactness | table, one slide per element or group | `members`, `reach`, `exactness` |
| Decision | What Tim is asked, with the options | the deck's decision slide | the handoff's questions |

Because every drawing is a function of the checked source, a name or a relation cannot be changed in one view and left behind in another. Every node, connector and table row carries the declaration id as its target, so a narration beat and the lit element work as they do now, and the same element is lit across views. The generator splits a view that would not fit its slot (a component view of more elements than a slide holds) by container or group into several slides, rather than shrinking it.

The first three rows and the surface use only words the language has today, so they can be built before any language change. Context, runtime scenario and deployment need new words.

### What the language needs

Each is a proposal for the kit's publisher, and each word needs Tim's approval on its own, as every earlier word did (see the approval notes in `arch.yaml`). A language file change makes a kit release that waits for his review and makes earlier approvals of architecture stale, so these are best batched.

- `external`: a form for a person or a system outside the one described, with the words saying what it is and what it does. Needed by the context view.
- `uses`: a fourth relation, one element or external using another, with a line saying for what. Today `implements`, `answers` and `holds` say how code is built, not who talks to whom.
- `scenario`: a declaration of an ordered list of steps, each from one element to another with words. Needed by the runtime view and by the scenario the view set story already asks for.
- `runs on`: a way to say where an element or container runs, with a node or environment as a place. Needed by the deployment view.
- `decision`: a record of a choice, its context, the options considered and its consequence. Needed so the decision slide cites the architecture instead of repeating it.

### Standard view sets this follows

- The C4 model (Simon Brown) gives the zoom: context, containers, components, code, with dynamic and deployment diagrams beside them. It is the model for the first three rows and is widely known, so a reader who has seen it knows what each slide is.
- arc42 names the sections a description should cover: context and scope, solution strategy, building block view, runtime view, deployment view, cross-cutting concepts, architecture decisions, quality requirements and risks, glossary. It gives names for the runtime, deployment and decision views, and tells an author what to leave out and why.
- The 4+1 view model (Kruchten, 1995) gives logical, process, development and physical views tied together by scenarios. Its use of a few concrete scenarios to hold the views together is what the view set story already does today by walking one scenario through every view.

C4 labels the structural levels, arc42 labels the runtime, deployment and decision views, and the scenario thread from 4+1 stays. Quality requirements, cross-cutting concepts and risks are left out of the first version: the language has no words for them.

### The vote and the approval

- The standard vote stays what it is: a package with `approve-architecture` as its last question carries no `approve-package`, and the answer is the one vote.
- `approve-architecture` is asked on the decision slide, as any deck asks a decision on its slide, and in the question card as now.
- His approval is of the exact checked revision of the source documents, the subject recorded today (`package_inbox.subject_of`), not of the drawings. The drawings are a function of that revision and of the generator, so they are shown with the revision they come from.
- Staleness is unchanged: a newer checked revision of any source document, or a kit with different language files, makes the answer stale (`language_projection.current_subject`).
- The receiving JARVIS regenerates the views from the bound source and compares them with the deck, as it regenerates a deck's proof now (`presentation_proof.reprove`). A package that shows a view not derived from its bound source is refused.

### What stays

- The checked document, its revisions, the kit and its pinned digest, the check, `canonical.json` and the identity binding.
- The kit's rendered page, kept as the exact view of the source and opened from a link on the deck.
- Approval of an exact revision, its staleness rules, the `approval` flag in the handoff, and the answer returning to the sending session on sign-off.
- View sets: several documents on one Work item, with the same id naming the same element, each drawn into the same deck.
- Signing, the gate, the message that carries it, the package inbox and Done.
- Existing architecture packages continue to open as page packages.

## What it would take to build

Each piece is a separate change.

1. View generator: a module that reads a checked document (the parsed document `language_documents.page_data` already extracts) and writes presentation/1 objects for the views that need no new words: containers, components and surface, plus the decision slide. Splits views by container or group by the capacity rules. New code and its tests.
2. Deck assembly: compose a `presentation.yaml` from the generated slides, the author's narration and the handoff's questions, build it through the existing deck pipeline (`make_presentation`, the proof). Changes `jarvis/make_package.py` and `jarvis/language_projection.py`.
3. The author's contract: replace the author's `story.json` and `UNDERSTANDING.md` with a narration file naming the views and the words said over each; the purpose and conclusion become the opening slides. Changes `jarvis/package_author.py`, `docs/making-a-package.md` and the author's prompt.
4. The gate: regenerate the views from the bound source and compare, in place of the byte comparison of the story. Changes `language_projection.gate`, `package_story.compose` and `walk_problem`.
5. The page: an architecture deck opens as a deck package, with the exact-source link and a link to the kit's page. Changes `PackageView.tsx` for the link and `packages.ts` for how the package is classified.
6. The approval: moves from the story's last slide to the deck's decision slide, with the same subject and staleness. Changes `package_inbox.page_vote` and `package_inbox._story_questions`.
7. Language words: the five proposals above, as separate upstream requests, each approved on its own. When the kit publishes one, the generator gains the view that needs it (context, runtime scenario, deployment).
8. Tests and the release check: a corpus of architecture decks built and proved by `tests/test_presentation_corpus.py`, page tests at the checker's frame sizes, and the language-kit workflow.

Pieces 1 to 6 need no kit change and give containers, components, surface and decision. Piece 7 waits on the publisher.

## Open decisions for the owner

### views-from-existing-words-first

The situation: containers, components, the exact surface and the decision can be drawn from words the language has today, while context, runtime scenario and deployment need new words from the kit's publisher.

The choice is between building pieces 1 to 6 now and adding the other views as the words arrive, or waiting for the new words so every view ships at once.

Building now gives a package with several views soon, and the later views arrive without changing earlier packages. Waiting delays any change to architecture packages until the publisher has released and he has approved every new word.

Recommendation: build now.

### language-additions

The situation: the five words (`external`, `uses`, `scenario`, `runs on`, `decision`) each need his approval, and each batch of language changes makes a kit release that waits for his review and makes existing approvals of architecture stale.

The choice is which words to ask for and in how many releases: all five at once, `external`, `uses` and `scenario` first with `runs on` and `decision` later, or only the words he picks.

All at once means one review and one round of stale approvals. Several releases means more reviews and more stale approvals, but each is smaller. Leaving a word out means its view is not available.

Recommendation: `external`, `uses` and `scenario` first, giving the context and runtime views, then `runs on` and `decision` in a second release.

### view-naming

The situation: three standards name views, and the slides need names.

The choice is C4's names for the structural views with arc42's names for the runtime, deployment and decision views, or arc42's names throughout, or C4's alone with names of our own for the rest.

The mixed set matches what each standard is clearest about and keeps the zoom from C4. Using only arc42 gives one standard with longer, section-style names. Using only C4 leaves the runtime, deployment and decision views without a standard name.

Recommendation: the mixed set.

### explanation-document

The situation: today the package requires `UNDERSTANDING.md`, which the author writes and which he reads in a card. In the proposal the purpose and conclusion are the opening slides and the narration is said over each view.

The choice is to keep the document required, make it optional and linked from the deck, or retire it.

Keeping it required means the author writes the same content twice. Optional lets the author add a long-form document when the slides are not enough. Retiring it removes the option of a long document next to the deck.

Recommendation: optional, linked from the deck.

### approval-covers-the-drawings

The situation: his approval is recorded against the checked source revision. The drawings are generated from it by a program, and a change to the program changes the drawings without changing the source.

The choice is whether his approval is of the source revision alone, or of the source revision and the version of the generator that drew it.

Source alone keeps an approval standing when the program is improved, so a better drawing of the same architecture never asks him again. Including the generator version makes every generator change stale every open approval, so he is asked again about an architecture he has already approved.

Recommendation: source revision alone, with the generator version shown on the deck.

### authors-choice-of-views

The situation: the author supplies the narration and the choice of views.

The choice is a fixed list of views in a fixed order for every architecture package, or the author choosing which views to include with a stated reason for each omission, in the fixed order.

A fixed list makes every architecture package read the same way and leaves nothing to omit, but a small change would carry slides that say nothing. Author's choice keeps packages short, and the stated reason for each omission shows what the author judged not to need.

Recommendation: the author's choice, in the fixed order, with a reason for each omission.

### existing-packages

The situation: architecture packages delivered before the change are page packages with a story over the kit's page.

The choice is to keep opening them as page packages indefinitely, to convert them to decks when opened, or to retire the page form after a set time.

Keeping them as they are means two forms in the code. Converting changes what was approved and sent, and cannot regenerate narration the author wrote for the old form. Retiring on a date removes the old form but loses the old packages' stories.

Recommendation: keep opening them as they are, and remove the old form only when none is open.

### the-kit-page-as-exact-surface

The situation: the kit's page is the exact view of the document: every member and relation, as the language checks it.

The choice is to keep it reachable from the deck (a link, as the exact-source link is now), to replace it with the surface slides, or to drop it.

Keeping it gives the reader a way to inspect the whole source at once, and costs the link. Replacing it with the surface slides means the exact members are shown only where slides fit them. Dropping it gives up the view the kit's publisher maintains.

Recommendation: keep it reachable from the deck, and draw the surface slides from the same document.
