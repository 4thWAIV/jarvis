# Canonical architecture authoring

Adopt architecture first. For content the enabled language expresses, a versioned, checked YAML document is the only canonical source. The renderer, speech, summaries, diagrams, package discussion and agent follow-ups derive from its exact revision. They are views, not competing editable truths. Ordinary conversation still works; facts outside the language remain explicitly outside its coverage. Never force missing meaning into a vague string simply to claim complete coverage. Editing an architectural claim changes its document and regenerates views. Reading old prose is permitted; publishing new covered claims requires the canonical path.

A draft with pending fields remains a draft with visible checker output. Unknown language, unresolved imports, rejected check, or omitted meaning prevents publication as validated communication. The renderer may still make an inspection page, but rendering success alone is never the acceptance gate. Code verification and human approval are separate facts.

The enabled authoring capability is arch. Use language_document capabilities to inspect the current kit and coverage constructs. Use validate with source, Work linkage, scope revision, author, coverage and evidence. A correction supplies the original document_id and parent_revision. The Markdown explaining a revision is a view of the exact YAML; it does not establish semantic equivalence or approval, and YAML remains canonical. JARVIS's own brain supplies readable_markdown with validate, its hash bound to the immutable revision, and uses render or publish with the exact source_revision returned by validation. Follow continuation segments until the complete JSON envelope is recovered.

Use ground with the package ID to obtain its checked canonical identity. Supply document, revision and source revision as expected-value checks when already known. Include the inbox ID when discussing a particular arrival. Grounding returns the exact known canonical source, declared author Markdown and host-generated followup_reference. Include that reference in the addressed text passed to the existing capture tool, then read_capture and the existing approval/steer_session flow. No current DOM observation is claimed. The proposal state field does not grant approval.

An agent session has no language_document tool and never publishes. It runs capabilities, validate, retrieve, render and ground with the command python -m jarvis.language_document, giving its own session id with --as, every request signed with its own onboarded key, and gives no readable_markdown. It sends a checked revision to Tim only with python -m jarvis.make_package, giving the document id with --document, the exact revision with --revision, its handoff file with --handoff, its own engine (claude or codex) with --engine, its session id with --session and the Work item with --work: a fresh author writes the explanation, JARVIS projects the exact revision around it, and the package is signed, author-proven and delivered as a message on the document's Work item. the Architecture documents section of docs/making-a-package.md is that whole path. MetaLang and propose are carried with staged authoring adoption; EvoLang is unavailable in the approved release.
